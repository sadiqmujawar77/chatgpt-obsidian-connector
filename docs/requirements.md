\# System Requirements



\## 1. Purpose



The ChatGPT Obsidian Connector shall provide a local-first mechanism for capturing ChatGPT conversations and storing them as structured Markdown documents in an Obsidian vault.



The system shall separate browser-based conversation capture from local filesystem storage.



\## 2. Functional Requirements



\### FR-001 — Conversation Capture



The system shall allow a ChatGPT conversation to be captured from the browser.



The captured conversation shall include:



\- Conversation title

\- Conversation URL

\- Message roles

\- Message content



\### FR-002 — Message Extraction



The browser extension shall extract messages from the rendered ChatGPT conversation.



Each extracted message shall contain:



\- Role

\- Content



Supported roles shall include at least:



\- User

\- Assistant



\### FR-003 — HTML-to-Markdown Conversion



The browser extension shall convert captured message HTML into Markdown before sending the conversation to the local connector.



The conversion shall preserve common document structures, including:



\- Headings

\- Bold text

\- Italic text

\- Ordered lists

\- Unordered lists

\- Links

\- Code blocks

\- Blockquotes

\- Tables

\- Horizontal rules

\- Line breaks



\### FR-004 — Conversation Metadata



Captured conversations shall contain structured metadata.



The generated Markdown shall include YAML frontmatter containing:



\- ID

\- Title

\- Type

\- Project

\- Date

\- Tags

\- Source



\### FR-005 — Conversation Identification



Project conversations shall receive sequential identifiers.



For project `P001`, identifiers shall follow the format:



```text

P001-001

P001-002

P001-003

...

```



The identifier shall be generated by the local connector.



\### FR-006 — Markdown Generation



The local connector shall generate a structured Markdown document from the captured conversation.



The document shall contain:



\- YAML frontmatter

\- Conversation title

\- Summary section

\- Key Points section

\- Conversation section

\- Related section



\### FR-007 — Conversation Storage



The local connector shall store generated Markdown documents in the configured Obsidian vault.



Project conversations shall be stored under the project's conversation directory.



\### FR-008 — Markdown Save API



The connector shall provide an endpoint for saving Markdown content.



```http

POST /save

```



The endpoint shall accept a filename and Markdown content.



\### FR-009 — Conversation API



The connector shall provide an endpoint for saving structured conversations.



```http

POST /conversation

```



The endpoint shall accept:



\- Conversation title

\- Conversation URL

\- Conversation messages



\### FR-010 — Health Check



The connector shall provide a health-check endpoint.



```http

GET /health

```



The endpoint shall return the current service status.



\### FR-011 — Input Validation



The connector shall validate incoming requests before writing data to the filesystem.



Validation shall include:



\- Request type validation

\- Required field validation

\- Message structure validation

\- Message role validation

\- Message content validation

\- Filename validation

\- Request-size validation



\### FR-012 — Existing File Protection



The connector shall not silently overwrite an existing Markdown file.



If the destination file already exists, the connector shall reject the save operation.



\### FR-013 — Atomic File Writes



The connector shall perform safe file writes using a temporary file followed by an atomic replacement operation.



The implementation shall synchronize the temporary file before completing the replacement.



\### FR-014 — Local Network Binding



The connector shall listen only on the local loopback interface.



The default endpoint shall be:



```text

127.0.0.1:8765

```



The connector shall not intentionally expose its HTTP API on external network interfaces.



\## 3. Browser Extension Requirements



\### FR-015 — Manifest V3



The browser extension shall use the browser's Manifest V3 extension architecture.



\### FR-016 — ChatGPT Page Integration



The extension shall operate on supported ChatGPT pages.



The current supported host is:



```text

https://chatgpt.com/\*

```



\### FR-017 — Content Script Isolation



Conversation extraction shall be performed by an extension content script rather than page-context JavaScript.



\### FR-018 — Background Communication



The extension shall use a background service worker for communication with the local connector.



\### FR-019 — Local Connector Communication



The extension shall send conversation data to the local connector using HTTP and JSON.



\## 4. Obsidian Requirements



\### FR-020 — Markdown Compatibility



Stored conversation documents shall be standard Markdown files compatible with Obsidian.



\### FR-021 — YAML Frontmatter



Conversation documents shall use YAML frontmatter for structured metadata.



\### FR-022 — Project Organization



The system shall support organizing conversations by project.



The current project structure includes:



```text

00 - ChatGPT/

└── Projects/

&#x20;   └── P001 - ChatGPT Obsidian Connector/

&#x20;       └── Chats/

```



\## 5. Non-Functional Requirements



\### NFR-001 — Local-First



The system shall prioritize local processing and local storage.



Conversation documents shall be written directly to the configured local Obsidian vault.



\### NFR-002 — Privacy



The connector shall not require a third-party cloud storage service for storing the Obsidian vault.



\### NFR-003 — Minimal Dependencies



The local connector should minimize external runtime dependencies.



The current connector uses Python's standard library HTTP server implementation.



\### NFR-004 — Reliability



The connector shall validate input and protect existing files before performing filesystem operations.



\### NFR-005 — Data Integrity



File-writing operations shall minimize the possibility of partially written Markdown documents.



\### NFR-006 — Maintainability



The browser extension and local connector shall remain separate components with clearly defined responsibilities.



\### NFR-007 — Portability



Stored conversation data shall remain standard Markdown and YAML so that it is not dependent on a proprietary database format.



\### NFR-008 — Extensibility



The system architecture shall allow additional capture and knowledge-management capabilities to be added without replacing the core browser-to-local-connector architecture.



\## 6. Current Scope



The current implementation covers:



\- Local connector

\- Connector health check

\- Markdown save API

\- Conversation save API

\- Browser conversation extraction

\- HTML-to-Markdown conversion

\- Structured conversation generation

\- Sequential conversation identifiers

\- Local Obsidian storage

\- Input validation

\- Existing-file protection

\- Atomic file writes



\## 7. Planned Capabilities



The following capabilities are planned but are not required for the current core implementation:



\- Save the current ChatGPT response

\- Save selected text

\- Append content to an existing note

\- Project selection

\- Project creation

\- Automatic project indexes

\- Global conversation index

\- Previous and next conversation links

\- Related-conversation discovery

\- Searching previous conversations for existing discussions

\- Durable knowledge extraction from conversation archives
